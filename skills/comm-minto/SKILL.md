# Minto Review

A critique and rewrite of a piece of communication (email, message, report, memo, proposal, deck outline, update) using Barbara Minto's Pyramid Principle. The goal is a message the reader understands at once and can act on, and a writer who learns the method from each review.

## Trigger

Run only when the user explicitly calls this skill or asks for a "Minto review" by name. Do not apply it to ordinary drafting requests, even if the structure could be better. When it is not invoked, behave normally.

## Step 1: Confirm the draft and its reader

Identify three things before reviewing:
- **The draft:** the text to review. If none is given, ask for it.
- **The reader:** who will read it and what they already know.
- **The purpose:** what the reader should know, decide or do after reading.

If the reader or purpose is unclear and the draft does not reveal it, ask one question and wait.

## Step 2: Ground it in real context

Check whatever sources of truth the current project or workspace defines (its instructions, files, memory, templates, tone and language rules, and any connected tools). Use what is there; do not assume any specific document or tool exists. Respect the workspace's own rules for tone, language, format and confidentiality in the rewrite. If a fact needed to complete the message is missing, mark it as [missing] rather than inventing it.

## Step 3: Test the draft against the principles

Check the draft against these principles and note where it fails. Lead with the failures that hurt the reader most.

**1. Answer first (top-down)**
- Is the main point, decision or request stated in the first lines?
- Could the reader stop after the first paragraph and still know what matters?

**2. One governing thought**
- Can the whole message be summarized in a single sentence?
- If not, is it really two messages that should be split?

**3. Situation, Complication, Question (SCQ)**
- Does the opening set the shared context (Situation), what changed or went wrong (Complication), and the question that raises for the reader?
- Is the opening short, telling the reader only what they already accept plus what is new?

**4. Vertical logic**
- Does each point directly answer the question raised by the point above it ("why?", "how?", "so what?")?
- Is any point floating, with no clear link to the main message?

**5. Horizontal logic and grouping**
- Are the supporting points of the same kind (all reasons, all steps, all options)?
- Are they mutually exclusive and collectively exhaustive (no overlaps, no gaps)?
- Are there three to five groups rather than a long flat list?
- Are they in a deliberate order (time, structure, or importance)?

**6. Summarizing, not labeling**
- Do headings, subject lines and bullet leads state the actual point ("Supplier response time doubled") instead of a topic label ("Supplier update")?

**7. Reader effort**
- Is the request, deadline or next step explicit and easy to find?
- Is there anything the reader must work out alone that the writer could have said?

## Step 4: Write the review

Use this shape:

**Critique:** the main structural problems, strongest first, one line each. Name the principle each one breaks. If the draft is already well structured, say so plainly and keep the critique short.

**Rewritten version:** ready to use, in the same language, tone and format as the original (subject line included for emails). Keep the writer's facts and voice; change structure and wording only as much as the principles require. Mark any missing fact as [missing].

**What changed and why:** short notes, each tying a change to a principle (e.g. "Moved the request to line one: answer first").

**Suggestions:** two or three optional improvements not applied in the rewrite (e.g. split into two messages, add a deadline, attach the data, change the channel), one line each with the trade-off. Do not pick for the user unless asked.

## Rules

- Be direct and respectful; critique the text, not the writer.
- Do not roleplay Minto or quote her. Use the method, not the persona.
- Never add facts, figures, commitments or promises that are not in the draft or the sources.
- Keep the rewrite no longer than needed; shorter is usually better.
- Reply in the language the user writes in; keep the rewrite in the draft's language unless asked otherwise.
- The current project's or workspace's own rules (approval gates, tone, confidentiality, templates) still apply. Reviewing a draft never means sending it.
